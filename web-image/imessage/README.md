# iMessage 独立桥接

为同一个已确认的微信绑定增加 iMessage 文本通道，保留 Telegram 原有收发。NAS 网关为 `gateway.py`，Mac 进程与测试位于 `mac/`。实际部署状态以两端开关和进程读回为准；离线测试不代表真人已经收到消息。

网关通过 SSH 标准输入接收请求，不监听网络端口，不消费 Telegram 更新，不重启 EFB。私有配置固定唯一目标，调用方不能指定收件人。微信到 iMessage 只读取指定绑定的文本和附件索引，不读取 pickle 或其他会话正文。可选择将 Telegram 发往同一微信绑定的成功文字消息同步到 iMessage。

## 使用

Telegram 私聊 `/backend` 或 `/imessage` 提供桥接和图片同步两个开关。只影响 iMessage，不改变 Telegram↔微信或 HA 路由。面板依据 Mac 的实际回执显示状态；离线或回执过期显示等待连接，点击「刷新 iMessage 状态」重新读取。操作按钮五分钟过期，旧版本按钮不能覆盖新设置。

开启 `managed_control` 后，关闭桥接会保留 Mac 控制进程低频待机，因此可从 Telegram 再开启。它不会自动增加开机启动项；Mac 关机或控制进程退出时，远程开关只能等待连接。重新开启从当前时间处理消息，不补发关闭期间的内容。图片开关独立，快速关闭再开启也会更新图片时间边界，不改变文字消息起点。

Mac 桌面的「iMessage桥接」目录提供「开启.command」「关闭.command」「状态.command」。开启前先同步关闭旧轮次，再从当前时间处理新消息。当前采用手动运行方式，没有登录项或开机自启动；Mac 关机或重启后须重新开启。

文字与附件分别处理。图片已接通；文件、视频通过可选附件扩展接入。通知发送器沿用现有限流，连续消息可能排队；本来源最多保留 5 条待发送或发送中消息，不占满共享通知队列。

## 关闭与恢复

`off` 关闭专用通知路由并取消该来源的待发送项；HA 路由及全局版本保持不变。已在发送中的消息可能完成，不能撤销已发送消息。`on` 从当前日志末尾开始，停用期间的内容不会补推。重新启用会更新 epoch，拒绝旧轮次的提交。

iMessage 到微信复用现有低优先级通知发送器，因此遵守其普通聊天优先、10 秒全局间隔、30 秒路由间隔和 120 秒过期策略。未确认的发送结果不自动重试。该通道优先保障普通聊天；附件使用独立的有界队列。

## 部署前必要条件

- BlueBubbles 普通模式 API 可用，用户允许必要权限；不需要 Private API 或修改 SIP。
- Mac 与 NAS 之间有已核验主机密钥的 SSH 加密连接；不得把 API 密码放入命令参数或日志。
- Mac 端严格限定唯一 iMessage 会话，忽略自己发送、历史、反应及系统事件。
- 现有绑定已核实，程序与私有配置分离；备份后仅添加独立来源和路由。
- 日志时间按实际 EFB 时区解释，不能假定 UTC。
- 不以自动发送真实测试消息验收。启用前须有离线故障测试，启用后用用户自然消息的日志核实。

运行测试：`python3 -m unittest discover -s web-image/imessage -v`。

## 验证与回退

分别运行网关测试和 Mac 模拟测试：

```sh
python3 -m unittest discover -s web-image/imessage -v
python3 -m unittest discover -s web-image/imessage/mac -v
```

先用桌面的关闭入口停止双向转发，并读回 NAS 已关闭；原 EFB、Telegram 和 HA 无须重启。若 NAS 暂时不可达，本地立即关闭，远端关闭记为待同步，重新开启前必须完成关闭确认。已在发送中的消息可能完成。不要用整个旧配置覆盖现有绑定来回退。

API 密码、联系人白名单、SSH 凭据和生产配置只存私有目录，不提交到 Git。安装备份由生产环境保管，源码仓库只保存通用代码和说明。

## 发出文字的跨端副本

私有配置 `mirror_to_telegram=true` 时，只有 iMessage 通知队列明确记录微信发送成功，才发送一份正文后附加「（iMessage）」标记的 Telegram 副本。副本由本地 Bot API 直接发送，不进入微信发送队列。Telegram 调用结果不明确时不重试。

`mirror_from_telegram=true` 时，读取同一绑定的 Telegram 发往微信的成功文字记录并同步到 iMessage，排除失败记录。`mirror_since` 必须设为启用时的日志时间，防止首次启用补发历史。方向与消息编号共同去重。

两种副本均遵守原桥接开关。停用会取消等待中的副本；正在发送的请求可能完成。两端继续使用原绑定，不新增联系人、不改变 HA 路由。文字与附件分别验收，不能将文字镜像的测试结果当作附件验收。

## 图片功能

文件、视频扩展由两端私有配置 `attachments_enabled=true` 单独准入；NAS `attachments_since` 和 Mac 附件起点必须设为本次启用时间。旧客户端不接收附件。启用后，Telegram 的「图片与附件同步」统一控制图片和附件，总开关仍控制整个 iMessage 桥接。

单个附件上限 25 MiB，与图片共用最多 5 个待发或发送中位置和 120 秒时效。MP4 按视频发送；其他视频、文档和音频作为文件传递，不自动转码。文件名去除路径及控制字符，文件内容不执行。BlueBubbles 使用普通 AppleScript 附件接口，无须 Private API。

iMessage 附件仅在微信接口确认发送成功后复制到 Telegram。微信收到的附件，以及 Telegram 发往微信成功的附件，按同一绑定同步到 iMessage。发送结果未知不重试。BlueBubbles 内部可能自行重试 AppleScript，桥接单次调用不代表其内部只尝试一次。最终送达须用用户自然新发的文件和视频验收，禁止自动补发历史或发送测试消息。

回退时关闭两端附件配置并恢复旧镜像与独立 Mac 程序；保留当前游标、去重账本和绑定，不恢复旧消息状态。

2026-10-25 已部署：两端图片开关开启，网页版微信在线。绑定、HA 策略和网络配置保持不变。实际图片送达仍待用户自然发送后的记录验证，没有发送测试或补发旧消息。下文部署前检查用于后续重新部署。

Mac 端通过单次 SSH 标准输入流传输图片，正文不进入环境变量或命令参数。NAS 的 `image_pipe.py` 接收 `put/get`，`image_store.py` 保存有界临时队列，`image_outbound.py` 只向已消费的绑定消息签发短期下载授权。EFB 内的 `image_runtime.py` 复用现有登录通道发送图片，并在确认成功后向 Telegram 发送副本。

仅接受 JPEG/PNG，单张上限 25 MiB、2500 万像素。上传与待发图片最多 5 张，原始消息超过 120 秒不发送。切换、关闭或绑定变化取消待发项；结果不明确不重试。普通聊天和现有通知占用共享发送保护时，图片等待，不能抢占它们。

启用须同时满足 Mac 私有配置开关、NAS 私有配置开关及实时 `images_ready` 心跳。旧 Mac 文字客户端不会消费图片记录。NAS 用独立 `image_media_dir` 共享临时数据，EFB 用户只能读取必要状态；源令牌仍为 root 私有，不写入镜像。共享状态原子写入须保留属组和 0640 权限，先变更所有权再设置权限。

生产 EFB 没有动态加载此入口。候选镜像测试通过也不代表可以在零中断条件下启用；部署需要一次有计划的 EFB 进程替换，先说明暂停转发和可能重新扫码的影响。保存原镜像、Compose、私有配置和去重记录，避免回退时覆盖当前会话绑定或重新发送历史消息。

候选镜像已通过 31 项图片/网关测试、12 项菜单测试和 27 项通知回归测试。另有 UID/GID 101 隔离权限检查，验证能读取必要状态、写入图片数据且不能读取 root 私有文件。真实双向图片仍须在部署后用用户自然发送的新图片验收，不能主动补发或重复测试。

25 MiB 扩容：图片、文件和视频统一上限。Telegram 原图副本超过照片接口的 10 MB 阈值时使用文件方式上传，不压缩或重复发送。原图片 2500 万像素保护、75 秒传输截止、120 秒时效及普通聊天优先策略保留。

## 语音兼容

EFB 语音类型为 `Voice`，兼容旧 `Audio` 记录；仅处理启用后的当前绑定消息，不回放历史。微信语音通过现有文件索引读取，由现有运行镜像转换为 AAC/M4A 后交给 iMessage。Mac 端只对明确的原生音频标志、单音频附件、无应用气泡的消息放行语音 payload，不放开其他应用或系统消息。

iMessage CAF 录音转为 M4A 后，通过网页版微信文件接口发送；不会生成微信原生语音条。Telegram 副本使用音频播放器。图片和普通文件不转码。转换沿用 25 MiB 限制，并限定音频不超过 10 分钟、单线程、格式检查 3 秒、转换 10 秒；不静默截短，失败不自动重试。实际原生录音仍须用用户自然新发的语音验收，不主动发送测试内容。

## 稳定性维护与诊断

`/imessage` 面板显示最近 24 小时的附件异常分类：发往微信、Telegram 副本、读取发往 iMessage 的附件和附件服务。每个环节只保存最后一条时间、有限错误码及累计次数；不保存消息正文、文件名、地址、账号或异常原文。记录失败不会阻塞转发。未知结果不自动重试，面板无异常也不等于对端已经收到。

去重指纹持续保留，取消累计 1 万条附件和 10 万条转发记录后的硬停止。原有 5 条在途限制、25 MiB、120 秒有效期和关闭/轮次保护保持不变。已消费或过期的附件正文仍按原流程回收，不删除指纹，不通过清空数据库恢复容量。元数据仍随使用量增长，应定期查看磁盘空间；不能宣称无限存储。

## 发布、部署与回退

1. 通用代码和模拟测试提交到自有仓库；排除配置 JSON、SQLite、凭据、日志、附件、备份和本机清单。Mac 的凭据读取器由部署机器私有提供，不包含在仓库中。
2. PR 只构建与测试。只有自有主分支的手动工作流且 `publish=true` 才发布镜像；CI 不连接 NAS、不启动微信、不部署生产。
3. `maintenance=true` 保留锁定的基础运行环境，同时复制控制器和 iMessage 模块；完整 Dockerfile 用于明确批准的依赖升级。两个构建路径均运行离线桥接测试。镜像发布后记录提交和镜像摘要，不能只依赖可覆盖标签。
4. NAS 部署前备份 Compose、原镜像标识、主机桥接代码和私有配置；用 SQLite backup 保存绑定数据库。先确认微信在线、无在途消息，再仅替换网页版服务。主机网关更新须等新镜像恢复在线且心跳正常后进行。
5. NAS 回退恢复原 Compose/镜像和对应主机代码。保留当前消息游标、去重账本、绑定及登录凭据，不能整体还原旧状态造成补发。新增但未引用的独立模块可保留。
6. Mac 更新只处理独立桥接进程，保存开关状态和文字游标。附件起点使用启用或重启时刻，不补发旧附件。LaunchAgent 的实际安装与回退说明以 `mac/` 的部署文档为准。
7. 验收分为隔离测试、进程/心跳、配置与绑定比对、用户自然新消息送达。前三级通过不能替代最后一级，不主动发送测试或重放历史消息。
