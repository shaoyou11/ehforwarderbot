Opt-in file/video candidate — staging only, not an activation script

The installed text/image bridge is unchanged by preparing this folder. Do not deploy until NAS attachment protocol/config readiness has been confirmed by the primary task. This candidate does not generate messages or replay history.

Runtime files (all seven must be installed together): bridge.py, image_api.py, image_transfer.py, attachment_api.py, attachment_names.py, ssh_images.exp, ssh_stdio.exp. Existing image_api.py and ssh_stdio.exp behavior is unchanged. Old image/managed activation scripts do not copy attachment_api.py and must not be used unmodified for this candidate.

The private Mac config must explicitly set attachments_enabled=true to enable new files; absence/default is disabled. The existing images_enabled desired/applied switch gates both images and files. Text and image processing retains the existing whitelist, worker lock, persistent ledger, epoch, revision, overlap, 120-second and 25-MiB behavior. No new listener, background launch service, separate messaging account or retry loop is added.

Each newly opted-in worker records an independent attachment floor at construction and refreshes/persists attachment_start_ms at worker start. The upgrade-only --preserve-text-state worker invocation preserves the prior active text start/cursor/epoch on its first valid NAS sync; the cursor then advances normally. Ordinary worker starts retain the prior restart behavior. A newer control revision, image off/on, epoch change, bridge re-enable, readiness recovery or connection recovery advances the effective file floor to now, without resetting the text floor solely because an image/file switch changed. This prevents pre-deployment and disconnected-gap file replay, even when the text floor predates activation. NAS must use the same clean_filename canonicalization, including the 240-byte UTF-8 cap, before deployment. NAS independently enforces attachments_since; set its activation time on NAS, not in this public bundle.

Incoming files are considered only from BlueBubbles' exact configured-chat query and fresh incoming, non-system/non-reaction/non-sticker attachments. Existing JPEG/PNG/HEIC/HEIF remain on the old image path; other image MIME types remain unsupported. File downloads use GET attachment/{guid}/download?original=true&force=false. The original bytes are not transcoded or executed. Normalized NFC filenames remove paths/control characters/double quotes, are limited to 180 characters and 240 UTF-8 bytes (retaining a short ASCII extension when the byte cap applies), trimmed again after truncation for idempotence, and default to attachment.bin. Valid MIME strings are lowercase, bounded to 100 characters and default to application/octet-stream when missing/unsafe. MP4 by MIME or .mp4 extension requires at least 12 bytes and bytes[4:8]==b'ftyp'; other videos/audio/documents are opaque files. No media probe, codec installation or conversion is needed.

BlueBubbles send: ordinary apple-script multipart POST message/attachment with chatGuid, tempGuid, method, name, attachment. The name field preserves the cleaned Unicode display name. Content-Disposition uses a safe ASCII fallback and percent-encoded RFC 5987 filename*; quotes and CRLF cannot add headers. Only one HTTP send is attempted by this adapter. BlueBubbles itself includes AppleScript retry/fallback behavior; bridge ledger unknown events are never automatically retried, and this does not promise exactly one underlying AppleScript invocation.

NAS stream protocol remains on image_pipe.py: image put headers are unchanged. File put adds only filename to epoch/event_id/created/size/digest/mime. Poll opts in with images:true plus attachments:true only when both the existing image switch and the explicit local file flag allow it. File poll items have kind:attachment plus id/image_id/size/digest/mime/created/filename. Get header stays epoch/image_id. Response kind and filename must match poll exactly, as must size/digest/mime/created. Strict digest/offset/completion validation occurs before any Messages send. The existing 8192-byte chunks, 25-MiB cap, 75-second timeout and cancellation callbacks remain. NAS owns the shared five-pending cap.

File bytes are carried only in private 0600 spool files under private temporary directories, removed after use, and never in process arguments, environment, stdout logs or public paths. A <=2048-byte UTF-8 metadata header is represented by a bounded hex environment value and sent as binary UTF-8 bytes after authentication; this avoids Tcl 8.x corruption of astral Unicode filenames. This envelope contains metadata only, never payload data. Images retain their original header fields and framing.

Validation: the full working project passed 164 unit tests, including the eight legacy activation-helper checks not included in this runtime bundle. This bundle independently runs 156 tests with: python3 -m unittest discover -s <this-directory> -q. Tests use only synthetic data and mocks. verify_attachment_stream_mock.py explicitly runs a standalone, stateless remote Python simulator over the protected SSH transport: 2-MiB synthetic file put/get and a 179-character Unicode filename (239 UTF-8 bytes); it does not invoke gateway.py, image_pipe.py, EFB, Messages, Telegram, WeChat or shared production queues. The existing image framing was separately verified with a synthetic 2-MiB put/get simulator. No real file/video delivery has been tested.

Deployment/rollback must back up private code/config, stop only the independent worker, copy all seven runtime files, enable the private Mac attachment flag only after NAS readiness, and restart the independent worker with --preserve-text-state: the new attachment floor starts now, while the existing active text epoch/start/cursor are preserved. activate_attachments.py performs this guarded upgrade and requires matching NAS filename outputs before changing anything. Preserve desired bridge/image settings and the current ledger. Never restore an older state.db or resend unknown events. Leave EFB/Telegram/WeChat processes alone unless separately authorized by the user through the primary task.

Rollback retains any newly introduced, unreferenced modules. Restore only backed-up code/config; do not delete files. The restored bridge does not import the retained attachment modules.
