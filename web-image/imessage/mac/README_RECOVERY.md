Independent Mac login recovery

Scope: one user LaunchAgent, label local.imessage-bridge, installed only in ~/Library/LaunchAgents/local.imessage-bridge.plist. It executes the existing managed bridge worker with --launchd-worker, using the existing /usr/local/opt/python@3.13/bin/python3.13 entry point. RunAtLoad + KeepAlive keep the closed managed controller in its existing low-frequency standby. ThrottleInterval=30 bounds crash respawn. No root daemon, other service, SIP/permission, sleep/network or remote account setting is changed.

Requires the user to log into the graphical macOS session. This does not promise operation before graphical login, at FileVault unlock, or while the Mac is asleep/offline. No login/logout or reboot is forced for testing. The installed stable Homebrew Python path, private bridge config, normal Apple permissions and the existing NAS connection remain dependencies.

Desired control is always read from NAS first; startup never calls on/off. Desired=false stays closed/idle and does not open BlueBubbles. With desired=true and the NAS ready, a read-only authenticated local /api/v1/ping checks BlueBubbles. If the app is absent, the same wrapper may run open -gj -a /Applications/BlueBubbles.app once per graphical login. A private boot/console-session marker prevents loops across worker restarts; a running app is never reopened. This starts only the existing app in its ordinary mode. BlueBubbles auto_start=0 and auto_start_method=unset remain unchanged. It does not alter app preferences, grant permissions, bypass prompts or turn on forwarding. If the app/API remains unavailable, the existing managed bridge acknowledges actual enabled=false/paused_backend and never polls/consumes messages. Recovery advances current-time floors and leaves the ledger intact. No old messages are replayed.

Process ownership: desktop on/off/status scripts keep their current commands. bridge.launch detects the private service registration and delegates to launchctl, never to a second Popen. A running job is left alone; an idle job gets kickstart without -k; an unloaded own job gets bootstrap of its exact own plist. The existing worker.lock remains the final single-instance fence. Direct independent worker CLI use while the agent owns it is unsupported; use the service controls instead.

Only bridge.py changes from the prior runtime. Required new modules: launch_service.py and service_worker.py. bridge_diagnostics.py is read-only, optional diagnostics; install_launch_agent.py provides own-service check/install/status/stop/start/uninstall. The agent contains no credentials, secret environment, URL or automatic on command. Stdout/stderr go to /dev/null to prevent payload/secret tracebacks or unbounded logs. A bounded, atomically replaced private 0600 service_status.json records only readiness booleans, accepted phase, timestamps and coarse failure classes, never message IDs/text/file names/accounts/addresses or exception strings.

Use the installer from this candidate with check or install. It requires a locally captured baseline (--baseline <private-baseline.json>, or the private candidate default); that host-specific baseline/manifest is deliberately excluded from public source exports. After installation, runtime controls are:
  python3 <bridge-home>/code/install_launch_agent.py status
  python3 <bridge-home>/code/install_launch_agent.py stop
  python3 <bridge-home>/code/install_launch_agent.py start
  python3 <bridge-home>/code/install_launch_agent.py uninstall
Stop/start operate only the own job and preserve NAS desired. Uninstall boots out only this label and moves its plist/registration into a private backup; it does not delete files or change remote settings. Runtime modules and the current ledger remain. Once registration is absent, manual scripts return to the prior standalone launcher. Code upgrades must first boot out this own job, because KeepAlive intentionally restarts a signalled process; do not kill just its PID and then copy code. Installation rollback archives only the new service files, restores prior bridge code, retains orphan helper modules/config/current ledger and resumes the old manual worker if it existed. Never restore an older state-audit.db.

Ledger inspection uses read-only aggregate counts and size/free-page metadata. A small ledger requires no deletion, vacuum, pruning or replay. Unknown records retain their permanent anti-duplicate fence; target-specific counts and host inventory are not included in the public export. The minimum diagnostic candidate is a read-only metadata snapshot (bridge_diagnostics.py): counts/status/control readiness and the latest bounded safe failure category. It does not guess the cause of a historical unknown result from ledger counts or read message bodies/raw app logs. No new notification/monitor or retry channel is added.

Validation: 199 working-project tests passed, including closed desired, dependency waiting/recovery from now, no on/off from startup, no poll while BlueBubbles is unavailable, once-per-login app opening, no reopen of an already-running app, manual-launch delegation without duplicate Popen, safe diagnostics, retained unknown ledger records and all prior text/image/file/video/voice/25-MiB regressions. The full candidate excludes eight older image/managed activation-helper tests and independently runs 191 tests. The minimal public incremental export contains only needed runtime/helpers, five test modules and this README; it independently runs 82 tests. All message tests are mocks. Installation performs only one real own-job stop/read/start cycle plus three fresh actual acknowledgements after each start; it never sends a test message or changes Telegram desired. Actual reboot/logout recovery is not forced or claimed as tested.
