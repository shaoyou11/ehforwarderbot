Voice metadata candidate — staging only; no deployment or test sends

Read-only findings from installed BlueBubbles 1.9.9:
- MessageSerializer.ts exposes isAudioMessage on ordinary non-notification message responses; hasPayloadData is !!message.payloadData; balloonBundleId is copied from message.balloonBundleId. Message.ts maps these to is_audio_message, payload_data and balloon_bundle_id.
- The one exact locally authorized chat was queried read-only using bound chat.guid, never other conversations or message text. The bounded audio-attachment metadata query found zero rows; a separate scoped native is_audio_message=1 count also returned zero, including messages with missing attachments. Consequently no actual native-audio field combination has been observed, and a native-voice drop cannot be claimed as proven from local samples.
- The deployed incoming_attachments filter unconditionally rejects truthy hasPayloadData or balloonBundleId. A fresh native voice with hasPayloadData=true would therefore be skipped even when its audio attachment is otherwise allowed. Audio attachments without those flags already use the generic file path.

Minimal candidate change (deploy bridge.py and attachment_api.py together, never only one):
bridge.py adds native_audio_payload_allowed and changes only the hasPayloadData branch in incoming_attachments. A payload exception requires isAudioMessage is exactly boolean true, empty balloonBundleId, exactly one attachment, nonempty GUID, integer size 1..25 MiB, no outgoing/sticker flag, and a known audio MIME/cleaned filename extension pair, including narrowly inferred missing metadata as described below. CAF, M4A/audio-MP4, MP3 and AAC have explicit finite pair sets. Unknown/non-audio MIME, mismatched extensions, documents/images/video, multiple attachments and arbitrary application payloads remain rejected. Existing item/group/association/from-me/age/floor checks execute before or after this narrow gate as before. Nonempty balloonBundleId remains rejected even when isAudioMessage=true; no native app-bundle exception is invented without a real sample.

For explicit native audio with no app balloon only, attachment_metadata fills a missing/empty transferName from a known audio MIME (for example Audio Message.caf), or fills missing/empty/octet-stream MIME from a known audio extension. It never overrides a conflicting or malformed MIME and never invents both missing fields. Other files keep the prior metadata behavior. The same metadata helper is used by the payload gate, original download validation and upload header, so filename/MIME stay consistent across the unchanged NAS protocol.

No protocol, config or service changes are needed on Mac. Existing images_enabled plus explicit attachments_enabled, 25 MiB, 75-second stream deadline, 120-second freshness, epoch/revision/off fences, attachment floor and persistent unknown-result dedupe remain. Original audio bytes use GET attachment/{guid}/download?original=true&force=false. The existing put/get attachment protocol preserves filename/MIME. NAS may handle Voice/CAF conversion; Mac does not transcode or mark a native voice bar.

Reverse M4A/audio can already be sent with ordinary POST /api/v1/message/attachment (chatGuid,tempGuid,method=apple-script,name,attachment). Current multipart intentionally omits isAudioMessage, so the server defaults it false and avoids implicit MP3-to-CAF conversion. The deliverable is a playable audio file; Messages' final presentation and native voice-bar behavior have not been tested or promised.
